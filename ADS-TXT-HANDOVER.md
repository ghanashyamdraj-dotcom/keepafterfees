## 2. What was verified live today (all read-only)

Every check below passed. This is the evidence that the file itself is not the
problem, and it is worth re-running rather than trusting, since it is three days
old the moment you read it.

**The file serves correctly**

```
HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 59
CF-Cache-Status: HIT
Server: cloudflare
```

**Contents are exactly one correct line, with a trailing newline and no BOM**
(confirmed byte by byte with `od -c`):

```
google.com, pub-9546036902768059, DIRECT, f08c47fec0942fa0
```

**The publisher ID matches the account.** `site.json` → `adSlots.clientId` is
`ca-pub-9546036902768059`; the build derives the `pub-` form from it rather than
requiring the number to be typed twice, so the two cannot drift.

**Every URL variant resolves**

| Variant | Result |
|---|---|
| `https://keepafterfees.com/ads.txt` | 200 |
| `https://www.keepafterfees.com/ads.txt` | 200 |
| `http://keepafterfees.com/ads.txt` | 200 (redirects to https) |

**Google's own crawlers are not blocked** — fetched with each UA explicitly:

| User agent | Result |
|---|---|
| `Mediapartners-Google` | 200 |
| `AdsBot-Google` | 200 |
| `Googlebot` | 200 |

**robots.txt does not block it.** There *is* a `Disallow: /` in the file and it
looks alarming in a grep — it belongs to `User-agent: Bytespider` only, a
deliberate block on a known bad actor. The catch-all `User-agent: *` is
`Allow: /`. Full file is 53 lines; read it whole before concluding anything from
a grep hit.

## 3. What has NOT been checked

These are the gaps. None was investigated, because the ask was to document
rather than act.

- **How the site is registered in AdSense.** The dashboard row reads
  `keepafterfees.com`. Whether it was added as the apex or as `www.` matters for
  which host Google looks at, and it has not been confirmed which one is
  recorded on the account.
- **Whether "Request review" has ever been clicked.** The status is
  *Getting ready*, and a previous session flagged that it was never confirmed
  whether review was actually requested or whether the site is simply sitting in
  the dashboard unsubmitted. Whether ads.txt is even re-crawled for a site in
  that state is unknown.
- **Whether AdSense offers a manual re-check.** Not looked for.
- **Cloudflare bot protections.** The file is served from Cloudflare cache
  (`CF-Cache-Status: HIT`) and answered every Google UA from this machine — but
  a request from this machine is not a request from Google's crawler IPs, and
  Bot Fight Mode / managed challenges can treat those differently. The
  Cloudflare dashboard settings for this zone were not reviewed.
- **Whether anything changed between 22 and 23 Aug** that would make the 22 Aug
  reading meaningful rather than simply early.

## 4. Useful context carried over

- The site auto-deploys from `main` via Cloudflare Workers Builds, ~80 seconds
  from push. Confirmed twice today.
- `ads.txt` is **generated by the build** (`build/build.mjs`), not a static file.
  `dist/` is wiped on every build, so a hand-placed file there survives exactly
  one deploy — this is why it is generated. Do not hand-place it.
- The AdSense loader script is emitted once per page in `<head>` by
  `layout.js`, gated on `site.json` → `adSlots.enabled`, which is `true`.
- One real ad unit is now live: the leaderboard slot carries
  `1805655779` (horizontal responsive) on the homepage, all 26 tool pages and
  every section index. The other four slots (`result`, `midContent`,
  `endContent`, `rail`) are reserved but empty by design — see `HANDOVER.md`
  §2.7.
- Everything is committed and pushed. Working tree is clean; the live site
  matches `main`.

## 5. Reproducing the checks

```bash
curl -sI https://keepafterfees.com/ads.txt
curl -s  https://keepafterfees.com/ads.txt | od -c
curl -s -o /dev/null -w '%{http_code}\n' -A "Mediapartners-Google" https://keepafterfees.com/ads.txt
curl -s  https://keepafterfees.com/robots.txt
```

One machine-specific gotcha: DNS here sometimes returns IPv6-only records for
this domain with no local IPv6 route, so a plain `curl` can fail even when the
site is fine. It worked today. If it stops working, use
`curl --resolve keepafterfees.com:443:<cf-ip>` rather than concluding the site
is down.
